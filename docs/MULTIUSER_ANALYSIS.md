# تحليل دقيق: نظام المستخدمين المتعدد + عزل البيانات + تتبّع النشاط

تاريخ: 2026-06-09 | المرجع: تسجيلات عمر الصوتية (مفرّغة).

## المطلوب (من عمر)
1. **أدمن** يضيف/يدير المستخدمين + يشوف كل شيء + يتتبّع الاستخدامات (مين سوّى إيش).
2. **موظف (clerk)** يدخل فواتير + يضيف عملاء، **وبياناته معزولة باسمه** (يشوف فقط ما أنشأه هو).

## الوضع الحالي (فحص فعلي للكود)
- ✅ جدول `User` (role: admin/clerk/accountant, isActive).
- ✅ `Invoice.issuedById` + علاقة `issuedBy` موجودة — لكن غير مفعّلة للعزل.
- ✅ `AuditLog` موجود (userId, entityType, action, old/newValues) — شبه غير مستخدم.
- ❌ `Subscriber` بلا حقل مالك (`createdById`).
- ❌ لا عزل بيانات (الكل يرى الكل).
- ❌ لا صفحة/API لإدارة المستخدمين.
- ❌ لا عرض لسجل النشاط للأدمن.

## النواقص + التكاملات
| # | الناقص | التكامل |
|---|--------|---------|
| 1 | Subscriber بلا مالك | + `createdById` (migration) + تعبئته عند الإنشاء |
| 2 | Invoice issuedById غير مُعبّأ | تعبئته تلقائياً = المستخدم الحالي |
| 3 | لا عزل | فلترة الاستعلامات: clerk → `where createdById/issuedById = me`؛ admin → الكل |
| 4 | لا إدارة مستخدمين | صفحة `/users` (admin فقط) + API CRUD للمستخدمين |
| 5 | AuditLog غير مفعّل | كتابة سجل عند كل create/update/delete + صفحة عرض للأدمن |

## خطة التنفيذ (مراحل)
1. **Migration**: `Subscriber.createdById` + index. (بدون كسر البيانات الموجودة → nullable.)
2. **عزل البيانات**: تعديل APIs (subscribers GET/POST, invoices GET/POST) لفلترة حسب الدور.
3. **إدارة المستخدمين**: API `/api/users` (admin only) + صفحة `/users` (إضافة/تعطيل/حذف موظف).
4. **سجل النشاط**: helper يكتب AuditLog + صفحة `/activity` (admin only).
5. **واجهة**: إخفاء عناصر الأدمن عن الموظف (صفحة المستخدمين/النشاط) + إضافة لروابط التنقّل بشرط الدور.

## أسئلة للتأكيد قبل التنفيذ
- البيانات الموجودة حالياً (بلا مالك) → تُنسب للأدمن افتراضياً؟ (مقترح: نعم)
- الموظف يقدر يشوف/يطبع فواتير عملائه فقط (مو عملاء غيره) → مؤكّد.

## ملاحظات إضافية (تسجيل 3 + صور نظام التحصيل المرجعي)
- البيانات الحالية = **بيانات اختبار** → آمن نسبها للأدمن / البدء نظيف عند التنفيذ. ✅ (جواب سؤال الترحيل)
- تبي **الأزرار منظّمة** عند المستخدمين.
- مرجع بصري: نظام "تسديد فواتير" (docs/ref-collection-system-*.jpg).

### نمط اختيار العميل المطلوب (من صورة نظام التحصيل)
- زر اختيار العميل = **أيقونة صغيرة في الشريط العلوي** (👤+) — مو زر كبير يأخذ مساحة.
- عند الضغط → **قائمة منبثقة** فيها:
  - حقل بحث بالأعلى (أيقونة عدسة).
  - قائمة العملاء كبطاقات: `رقم العميل - الاسم (الهاتف)` + **المبلغ المستحق بالأحمر**.
  - زر "عودة" بالأسفل.
- الحالة: ⏳ مسجّلة. (لم يبدأ التنفيذ — عمر سيرسل المزيد.)

## تسجيل 4 — متطلبات معمارية + مزايا جديدة
1. **تحليل قاعدة بيانات بعمق** + تصميم schema متكامل ومنظّم واحترافي لكل ما يُضاف.
2. **خطة متكاملة** حسب المعايير العالمية قبل التنفيذ — تطبيق فاخر متكامل.
3. مزايا جديدة مطلوبة:
   - **ملف شخصي (Profile)** لكل مستخدم/موظف.
   - **عزل المشتركين** لكل موظف (متوافق مع نظام الأدوار أعلاه).
   - **كشف حساب (Account Statement)**:
     - لمشترك واحد أو عدّة مشتركين.
     - يعرض العمليات/الفواتير **بالتاريخ** (تسلسل زمني للإدخالات).
   - تصميم فاخر راقٍ.

## القرار: تنفيذ على مرحلتين
- **المرحلة A (واجهة/UX سريعة):** تحسينات جولة 3 (حذف الزر، 3×2، رسم بياني، فوتر، استايل فاخر، قائمة الزر الأوسط) + نمط اختيار العميل (أيقونة علوية + قائمة).
- **المرحلة B (معماري/backend):** نظام المستخدمين + الأدوار + عزل البيانات + إدارة المستخدمين + سجل النشاط + الملف الشخصي + كشف الحساب + إعادة هيكلة DB منظّمة.
